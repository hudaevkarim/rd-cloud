# Окружение разработки

Всё, что неочевидно в настройке машины. Три находки ниже найдены экспериментом,
а не взяты из документации: каждая из них ломала работу по отдельности и молча
проводила время.

## Что установлено

| Что | Версия | Где | Ставилось |
|---|---|---|---|
| Node.js | 22.23.3 LTS | `rd-cloud/tools/node` | portable zip, в git не попадает |
| PostgreSQL | 16.14 | `C:\rcdb\pgsql` + `C:\rcdb\pgdata` | бинарники EDB, распакованные из zip |
| Git | 2.56 | `C:\Program Files\Git\cmd` | уже была в системе |

Docker не используется и не нужен.

## Первая настройка PowerShell

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

Один раз, вручную, права администратора не нужны. Без этого PowerShell блокирует
все `.ps1` — включая скрипты в `tools/`.

## Ежедневный запуск

```powershell
.\tools\pg-start.ps1# поднять PostgreSQL
. .\tools\env.ps1            # node, npm, git и переменные из .env в PATH
npm install
npm run db:migrate          # применить миграции
npm run db:seed             # создать первого администратора
npm run dev                 # сервер
npm run dev:web             # клиент
```

Остановить сервер базы: `.\tools\pg-stop.ps1`

## Находка 1: PostgreSQL не переваривает кириллицу в пути

```
FATAL:  invalid byte sequence for encoding "UTF8": 0xf0 0xee 0xec 0xe0
```

`0xf0 0xee 0xec 0xe0` — это «роман» в cp1251. PostgreSQL на Windows открывает
файлы через ANSI-кодовую страницу системы, а здесь она `cp1251`, и путь с
кириллицей он прочитать не может.

**Что из этого следует:**

- кластер лежит в `C:\rcdb`, а не в репозитории;
- `postgres.exe` тоже лежит вне репозитория — с бинарниками по кириллическому
  пути он тоже не стартует;
- данные приложения (`DATA_DIR=./data`) остались в репозитории: их читает Node,
  а он с такими путями работает.

Проверено отдельно, что `npm`, `tsc`, `esbuild` и Prisma с кириллическими
путями справляются. Негоден только сам Postgres.

### Почему не Docker

Прав администратора на машине нет. Docker Desktop требует админа на установку и
WSL2 или Hyper-V на запуск; нативный установщик PostgreSQL ставит службу Windows
и тоже требует админа. Официальные бинарники в zip запускаются обычным
процессом от текущего пользователя — это настоящий PostgreSQL 16.14, а не
эмулятор.

Отвергнутый вариант был — npm-пакет `embedded-postgres`: в реестре **все** его
версии помечены как beta.

Параметры кластера: `scram-sha-256`, `UTF8`, `lc_collate=C`, data-checksums
включены, слушает только `127.0.0.1:5432`.

## Находка 2: за тегом `latest` лежит release candidate

```
prisma@latest      = 8.0.0-rc.19   ← RC с переделанным CLI
prisma@prev        = 7.10.0         ← настоящий стабильный
@prisma/client@latest = 7.10.0
```

У 8-й версии CLI совсем другой: `contract`, `db`, `platform`, и нет ни
`generate`, ни `migrate`. Поэтому в проекте закреплена **7.10.0**.

У неё три отличия от привычного, и все обязательные:

1. **`prisma.config.ts` в корне** — `url` убрали из `schema.prisma`;
2. **генератор `prisma-client`**, а не `prisma-client-js`, поле `output`
   обязательно;
3. **driver-adapter обязателен**:
   ```ts
   const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
   const prisma = new PrismaClient({ adapter });
   ```

Ещё: клиент генерируется **TypeScript-исходником**, поэтому сервер запускается
через `tsx`, а `.env` больше не подхватывается автоматически — в
`prisma.config.ts` нужен `import 'dotenv/config'`.

Проверено на этой машине полностью: `generate` → `migrate dev` → `create` /
`findMany` / `deleteMany` с кириллицей.

## Находка 3: `.ps1` без BOM ломает разбор

Windows PowerShell 5.1 читает `.ps1` без BOM в ANSI-кодовой странице. Русские
комментарии превращаются в мусор, и скрипт падает с ошибкой разбора. Все
скрипты в `tools/` записаны в **UTF-8 с BOM** — при правке это нужно сохранять.

## Следствие: кириллица не передаётся аргументами командной строки

PowerShell отдаёт аргументы нативным программам в cp1251, а они ждут UTF-8. Тот
же `psql` отвечает на это:

```
ERROR:  invalid byte sequence for encoding "UTF8": 0xe8 0xe7 0x20
```

**Правило проекта:** SQL и текст передаются файлами (`psql -f`), а не
аргументами `-c`. Внутри приложения проблемы нет — оно работает с UTF-8 через
Node и драйвер `pg`.

В файлах, перенесённых из `rd`, осталось три символа `U+FFFD` — и они

в `fb2.test.ts` они описывают, как выглядит «замена битых байтов». Ещё три
порчи (`пробов??ть`, `гла??а`, `вр??д`) и опечатка `ампersandы` починены при
переносе.

## Находка 5: коллация `C` не умеет регистр для кириллицы

База, созданная с `LC_COLLATE = 'C'` (так она делается ради
воспроизводимости), приводит регистр **только для ASCII**:

```sql
select 'анна' ILIKE '%Анна%';          -- false
select lower('Анна') = lower('анна');  -- false
```

Это не мелочь, а поломка поиска: запрос «анна» не нашёл бы комнату
«Анна Каренина», а сортировка книг по автору шла бы по байтам, а не по
алфавиту. Обнаружилось тестом `поиск публичных комнат`, который искал
«анна» и находил пустоту.

Лечится созданием базы с ICU-коллацией:

```sql
CREATE DATABASE rdcloud ENCODING 'UTF8' TEMPLATE template0
  LOCALE_PROVIDER icu ICU_LOCALE 'ru-RU' LOCALE 'C';
```

`LOCALE 'C.UTF-8'` на Windows не существует — это частая ошибка, и она
отвергается. Готовый скрипт: `tools/setup-databases.sql`.

После пересоздания базы администратора нужно выпустить заново: токен
хранится только в виде sha256, и взять его больше неоткуда.
